# پرامپت اجرایی تکمیل همیار تا نسخهٔ قابل استفاده

این متن را به عامل توسعه بدهید. مرجع وضعیت همچنان `docs/ROADMAP.md` است؛ این پرامپت مجوز ادعای قابلیت تکمیل‌نشده نیست. تاریخ تنظیم: ۲۰۲۶/۱۰/۱۳.

---

تو مسئول ادامهٔ توسعهٔ «همیار» هستی: محصول فارسی کلاس و جلسهٔ آنلاین برای مدرسه، شرکت و اشخاص. کار تو رساندن همین مخزن به محصولی قابل استفاده، زیبا، قابل نگهداری و آزموده است. از بازسازی بی‌دلیل پروژه یا عوض‌کردن پشته صرفاً برای تنوع خودداری کن. خروجی باید کد اجرایی، مستندات هماهنگ، آزمون و شواهد واقعی داشته باشد.

## ۱. پیش از شروع، واقعیت مخزن را تثبیت کن

`AGENTS.md` و اسناد PRODUCT، ARCHITECTURE، DESIGN_SYSTEM، SECURITY، RECORDING، ROADMAP و ADRها را بخوان. Git status، lockfile، نسخه‌های نصب‌شده و راهنمای محلی Next.js را بررسی کن. تغییرات موجود کاربر را حفظ کن. تصمیم معماری تازه باید ADR با مسئله، گزینه‌ها، هزینه، امنیت، محدودیت و مسیر بازگشت داشته باشد.

وضعیت هنگام نوشتن این پرامپت:

- Next.js App Router، React، TypeScript strict، CSS tokens، Vazirmatn محلی و Lucide نصب شده‌اند.
- پنل کلاس‌ها، اعضای نمونه، مرکز نظارت، تنظیمات، پشتیبانی و اتاق نمونه وجود دارند؛ زبان فارسی و RTL، تم روشن و تیره و موبایل پشتیبانی می‌شوند.
- دوربین و میکروفون فقط پیش‌نمایش واقعی محلی دارند. رضایت کاربر و پاک‌سازی trackها پیاده شده است. انتشار چندنفره وجود ندارد.
- تخته SVG، undo و export و چت فعلی محلی‌اند. با reload دادهٔ جلسهٔ محلی پاک می‌شود.
- جلوهٔ محدود صوتی فقط سطح میکروفون محلی را تحلیل می‌کند. نمونهٔ صدا ذخیره، ارسال یا log نمی‌شود.
- سیاست پایهٔ tenant/room و grants محدود LiveKit و adapter صدور توکن سمت سرور وجود دارند؛ endpoint join معتبر، session و repository متصل وجود ندارند.
- `/api/status` فقط اطلاعات عمومی اجرای وب را برمی‌گرداند. سلامت SFU، ظرفیت واقعی سازمان، CPU/RAM فیزیکی و حضور زنده از آن نتیجه نمی‌شوند.
- پشتیبانی فقط یک پیش‌نویس اعتبارسنجی‌شده با ذخیرهٔ صریح در مرورگر، حذف و دانلود متن دارد. تیکت سروری ثبت نشده و شمارهٔ پیگیری واقعی وجود ندارد.
- Better Auth، Drizzle، دادهٔ پایدار، LiveKit عملیاتی، TURN، Yjs مشترک، Egress و private storage هنوز متصل نیستند.
- پروژه روی Vercel منتشر است؛ Vercel میزبان وب و API کنترل است. رسانه و WebSocket تخته باید زیرساخت مناسب خودشان را داشته باشند.

این وضعیت را دوباره با کد تطبیق بده؛ اگر تغییر کرده، گزارش آغاز را اصلاح کن. هیچ اطلاعات دمو را عضو، میزبان، مصرف یا اتصال واقعی معرفی نکن.

## ۲. کیفیت تجربهٔ کاربری، شرط پذیرش است

همیار باید ساده، شیک و آرام باشد؛ کاربر برای پیدا کردن ورود به کلاس، صدا، تصویر، تخته یا پشتیبانی فکر اضافه نکند. صفحه را با کارت‌های تکراری، متن ریز، نمودار بی‌منبع، برچسب‌های زیاد و دکمه‌های نمایشی شلوغ نکن. مدیر، معلم، دانش‌آموز و کاربر کم‌تجربه باید مسیر روشن داشته باشند.

رابط را با یک سیستم طراحی منسجم ادامه بده: مقیاس فاصله، شعاع، رنگ معنایی، تایپوگرافی، ارتفاع کنترل، border و shadow. گلس محدود و خوانا باشد؛ blur روی همهٔ لایه‌ها یا انیمیشن دائمی سنگین ممنوع. فونت محلی و فارسی خوانا، متن اصلی حداقل ۱۴ تا ۱۶ پیکسل، عنوان واضح، عمل اصلی مشخص، رنگ خطر فقط برای کار خطرناک. کارت، جدول، فرم، dialog، toast و empty state باید با یک زبان بصری ساخته شوند.

هر صفحه dark/light، RTL، عرض ۳۲۰ پیکسل، لمس، کیبورد، focus قابل مشاهده و reduced motion را پوشش دهد. وضعیت‌ها با متن و آیکن فهمیده شوند، نه فقط رنگ. کنترل حداقل ۴۴ پیکسل، ترتیب focus معقول، label واقعی، خطا کنار ورودی و اعلان قابل خواندن برای screen reader لازم‌اند. فرم بعد از خطا اطلاعات کاربر را نگه دارد. عمل destructive تأیید متناسب با همان عمل داشته باشد.

برای صفحهٔ کلاس، قرارگیری آشنا بماند: تصویر و افراد و گفت‌وگو در راست، ارائه/تخته بزرگ در چپ، عنوان بالا، کنترل رسانه پایین و خروج جدا. در موبایل تب‌ها داده را پاک نکنند. تعویض تب/تم و تمام‌صفحه نباید publication یا ضبط را قطع کند. متن آموزشی بلند در راهنما باشد. وضعیت reconnect، ضبط و درخواست مجوز همیشه قابل تشخیص باشند.

قبل از تحویل هر مرحله از صفحات اصلی در دو تم و دسکتاپ/موبایل تصویر بگیر و خودت بررسی کن. screenshot زیبا به‌تنهایی اثبات کارکرد نیست؛ مسیر کاربر باید واقعاً کار کند.

## ۳. ترتیب اجرا را حفظ کن

ترتیب پایه: حساب و جداسازی سازمان → مدل داده و مدیریت → تیکت سروری و سهمیه → prejoin و رسانه → کنترل و اتصال مجدد → چت/تخته مشترک → ضبط → نظارت کامل و گزارش → سخت‌سازی و آزمون عملیاتی. طراحی پنل‌ها می‌تواند همزمان تکمیل شود، اما API خصوصی قبل از session معتبر فعال نشود.

هر مرحله باید برشی قابل استفاده داشته باشد؛ فقط یک scaffold بزرگ با ده‌ها TODO نساز. برای هر برش، وضعیت قبل/بعد، معیار پذیرش، آزمون، مهاجرت و نحوهٔ اجرا را ثبت کن. نیاز به حساب خارجی، دامنه، هزینه یا credential را دقیق اعلام کن. secret نساز و در Git نگذار. خرید یا پذیرش شرایط سرویس جدید را از نیاز فنی جدا کن.

## ۴. هویت، سازمان و دسترسی

Better Auth را مطابق نسخه و مستندات معتبر به PostgreSQL وصل کن. ثبت‌نام/ورود، بازیابی حساب، تأیید ایمیل در صورت نیاز، خروج، مدیریت نشست و revocation داشته باش. cookieها HttpOnly، Secure و SameSite مناسب باشند. token نشست در localStorage نباشد. مدیر و سوپروایزر باید MFA داشته باشند؛ recovery و لغو نشست هم طراحی شوند.

سازمان‌های school/company/personal و عضویت مستقل بساز. کاربر ممکن است در چند سازمان نقش متفاوت داشته باشد. سازمان فعال از نشست معتبر و عضویت موجود تعیین شود؛ تغییر سازمان نباید نقش قبلی را منتقل کند. invitation یک‌بارمصرف، زمان‌دار، قابل لغو و محدود به نقش معتبر باشد. نقش از body درخواست قابل اعتماد نیست.

owner/admin/supervisor/member در سازمان و host/presenter/attendee در اتاق جدا باشند. مجوز نشر میکروفون، دوربین و صفحه مستقل و زمان‌دار است. پیش‌فرض deny؛ هم endpoint و هم دامنه سیاست را اعمال کنند. supervisor در تمام اتاق‌های سازمان خودش اختیار دارد. مدیر پلتفرم دسترسی ضمنی به کلاس مدرسه ندارد؛ break-glass با MFA، دلیل، scope، انقضا و audit جدا بساز.

تست منفی دو سازمان ضروری است: query، mutation، لینک ضبط، تیکت، websocket، گزارش و join با تغییر شناسه نباید اطلاعات سازمان دیگر را بدهند. پنهان‌کردن دکمه در UI امنیت محسوب نمی‌شود. مهمان باید invitation/room admission معتبر داشته باشد، نه tenantId دلخواه.

## ۵. مدل داده و مدیریت واقعی

Drizzle schema و migrationهای قابل اجرای نسخه‌بندی‌شده بنویس. User، Organization، Membership، Invitation، AcademicYear، Class، Subject، Enrollment، TeachingAssignment، Room، Session، RoomAssignment، MediaPermission، AttendanceInterval، Message، BoardDocument، Recording، SupportTicket، TicketMessage، QuotaPolicy و AuditEvent را متناسب با نیاز واقعی مدل کن.

تمام موجودیت‌های سازمانی organizationId داشته باشند. composite foreign key و unique scoped، index مناسب pagination و queryهای پرتکرار، transaction برای تغییرهای مرتبط و soft delete فقط با دلیل مشخص. scoped repository مرز داده باشد؛ UI مستقیم DB را نخواند. RLS با نقش غیرمالک و context تراکنش آزموده شود؛ connection pool context سازمان قبلی را نگه ندارد.

پنل مدیر امکان ایجاد/ویرایش/بایگانی کلاس و اتاق، تخصیص معلم، دعوت و غیرفعال‌کردن عضو، برنامهٔ جلسه، جست‌وجو، فیلتر و pagination واقعی داشته باشد. مدرس فقط کلاس‌های مجازش را ببیند؛ دانش‌آموز فقط enrollment معتبرش را. demo data در محیط production جای دادهٔ خالی ننشیند. empty state واضح با اقدام مجاز ارائه کن.

برند سازمان شامل نام، لوگوی امن، رنگ معتبر و تنظیمات اتاق باشد. HTML/CSS دلخواه ذخیره نکن. فایل لوگو private/public طبق سیاست صریح، نوع و اندازه محدود و پردازش امن داشته باشد. رنگ کنتراست کافی داشته باشد. تغییر تنظیمات با audit و مجوز سرور انجام شود.

## ۶. مرکز نظارت واقعی و ظرفیت قابل اتکا

مرکز نظارت را صفحهٔ اصلی عملیاتی سوپروایزر بساز. اتاق‌های واقعی با فیلتر وضعیت، میزبان واقعی، زمان شروع، شرکت‌کنندگان یکتا، درخواست‌های منتظر، وضعیت اتصال، ضبط و آخرین دریافت نمایش داده شوند. ورود/کنترل سوپروایزر، قفل/پایان جلسه، قطع publication، رسیدگی درخواست‌ها و اخراج فقط با مجوز سمت سرور و audit انجام شود. اقدام گروهی خطرناک تأیید و خلاصهٔ نتیجهٔ هر اتاق داشته باشد.

مشخصات را تفکیک کن: وب/API، SFU، TURN، تخته، worker ضبط، storage، DB و صف. میزبان/ناحیهٔ هر سرویس از deployment config معتبر یا telemetry همان سرویس گرفته شود. هویت مدرس از User/RoomAssignment و حضور از Session/participant معتبر گرفته شود. CPU/RAM، فضای دیسک و load فقط از exporter یا provider API معتبر نمایش داده شوند؛ حافظهٔ یک function را RAM کل سرور ننام.

هر metric منبع، واحد، زمان نمونه‌برداری و وضعیت fresh/stale/unavailable داشته باشد. زمان آخرین بررسی و دامنهٔ سنجش را نشان بده؛ HTTP موفق وب، سالم‌بودن تماس را ثابت نمی‌کند. secret، private IP، credential، URL امضاشده و شناسهٔ زیرساخت حساس فقط به نقش عملیاتی مجاز و در صورت نیاز نمایش داده شوند. خلاصهٔ عمومی وب کمینه باقی بماند؛ تمام مصرف و جزئیات سازمانی endpoint خصوصی داشته باشند.

سقف کاربران همزمان، تعداد اتاق، ناشران ویدیو، ضبط همزمان، فضای فایل/ضبط، نگهداری و پهنای باند را جدا مدل کن. مصرف با reconciliation رویدادهای SFU و session سنجیده شود؛ یک کاربر با reconnect یا چند event دوبار حساب نشود. ظرفیت باقی‌مانده فقط وقتی سقف و مصرف معتبرند برابر max(0, limit-used) است. null یعنی نامشخص؛ صفر یعنی ظرفیت تمام شده؛ unlimited یک سیاست صریح جداست.

کنترل سهمیه باید atomic باشد: دو join یا شروع ضبط همزمان نباید سقف را دور بزنند. reserve/commit/release و TTL رزرو و reconciliation خرابی را طراحی کن. reserved و active را تفکیک کن. ظرفیت خریداری‌شده با ظرفیت فنی آزموده‌شده یکسان نیست. اگر هر منبع stale است، رفتار پذیرش محافظه‌کار و پیام قابل فهم داشته باشد. نمودار تاریخچه فقط با دادهٔ واقعی و بازه/واحد مشخص بساز.

## ۷. ثبت و پیگیری تیکت سروری

پیش‌نویس فعلی را به فرآیند واقعی تبدیل کن؛ مهاجرت از متن محلی به ارسال فقط با اقدام کاربر باشد. ticketId واقعی پس از commit پایگاه داده نمایش داده شود. form شامل موضوع، دسته، اولویت، شرح و ارتباط اختیاری با اتاق/نشست باشد. ارتباط اتاق در همان سازمان سرور بررسی شود. فایل اختیاری پس از private storage و اسکن اضافه شود، نه آپلود عمومی آزاد.

مسیر وضعیت open/in_progress/waiting_for_user/resolved/closed، پیام‌های دوطرفه، تاریخچه، زمان ایجاد/آخرین پاسخ، مسئول مجاز، فیلتر، جست‌وجو و pagination داشته باش. اولویت انتخابی کاربر لزوماً SLA تضمین‌شده نیست. SLA واقعی اگر قرارداد دارد با timezone و ساعات خدمت محاسبه شود. بازگشایی، بستن و پاسخ با مجوز مشخص و audit باشند.

درخواست ثبت idempotency key، validation طول/نوع، origin/CSRF و rate limit توزیع‌شده داشته باشد. قطع پاسخ بعد از commit نباید تیکت تکراری بسازد. خطا نباید متن کاربر را پاک کند. عضویت سازمان، مالکیت و نقش پشتیبان برای خواندن/پاسخ بررسی شوند. پشتیبان پلتفرم با scope صریح به همان تیکت دسترسی داشته باشد؛ ticket مجوز مشاهدهٔ کلاس و ضبط نیست.

اعلان ایمیل/پیام تنها با سرویس و مقصد مورد تأیید و تنظیمات کاربر فعال شود. رمز، token و اطلاعات دانش‌آموز از log و telemetry دور بمانند. retention و حذف پیوست مشخص باشد. تست ثبت، تکرار درخواست، پاسخ، بستن، لغو دسترسی و حملهٔ شناسه بین دو سازمان بنویس. تا این مسیر کار نمی‌کند، هیچ پیام ارسال موفق یا شمارهٔ پیگیری جعلی نساز.

## ۸. prejoin و رسانهٔ چندنفره

صفحهٔ پیش از ورود انتخاب میکروفون/دوربین/خروجی در مرورگرهای پشتیبان، دوربین جلو/عقب، تست سطح صدا، وضعیت permission، و مسیر ورود فقط با صدا داشته باشد. getUserMedia فقط پس از action کاربر. خاموش‌کردن، خروج، pagehide، تغییر دستگاه، unplug و permission دیرهنگام باید تمام trackهای مربوط را آزاد کند. track آمادهٔ پیش‌نمایش با ownership روشن به transport تحویل داده شود تا capture تکراری ایجاد نشود.

endpoint join سازمان، عضویت، تخصیص اتاق، لابی، lock، ban، quota و grant را از DB/session معتبر بررسی کند. توکن LiveKit فقط server-only، کوتاه‌عمر، محدود به اتاق و publishSources لازم؛ roomAdmin هرگز در مرورگر. credential سرور در NEXT_PUBLIC یا bundle نرود.

LiveKit SFU، Redis، TURN/TLS، DNS و HTTPS/WSS را در زیرساخت مناسب راه‌اندازی کن. ارتباط UDP/TCP/TURN در شبکه‌های واقعی و ISPهای هدف آزموده شود. Vercel را media proxy نکن. adaptiveStream، dynacast و simulcast با تنظیم bitrate و سناریوی فقط صدا بررسی شوند؛ feature flag نصب‌شده برابر کیفیت آزموده‌شده نیست.

مجوز صحبت/دوربین/صفحه با درخواست، پذیرش میزبان و انقضا مدیریت شود. میزبان می‌تواند انتشار را قطع کند، ولی روشن‌کردن میکروفون/دوربین دیگری نیازمند رضایت همان فرد است. UI mute محلی و منع انتشار سرور را جدا بفهماند. اشتراک صفحه از user gesture آغاز شود؛ پایان native sharing وضعیت را اصلاح کند. قابلیت صدای سیستم/تب وابسته به مرورگر است و صریح توضیح داده شود.

## ۹. قطع شبکه و لغو دسترسی

ماشین حالت idle/connecting/connected/reconnecting/offline/denied/ended بساز. retry محدود با backoff و jitter، قابل لغو و بدون اتصال موازی بی‌انتها. هنگام reconnect نشست و مجوز دوباره بررسی شوند. پیام‌های کاربر صف محدود/idempotent و تخته resync داشته باشد؛ عملیات تکراری دوباره اعمال نشوند.

TTL توکن به‌تنهایی participant برقرار را اخراج نمی‌کند. مشکل revocation در LiveKit self-hosted مستندات SECURITY را واقعاً حل و روی signaling/SFU آزمون کن یا provider مناسب انتخاب کن. remove و webhook پس از اتصال جای جلوگیری از reconnect با توکن قبلی نیست. downgrade نقش، expiry grant، ban، پایان کلاس و revoke نشست باید روی اتصال باز هم اعمال شوند.

تست رفتاری: قطع ۵ و ۳۰ ثانیه، تغییر Wi-Fi به شبکهٔ همراه، tab پس‌زمینه، دستگاه جداشده، token منقضی، ban حین قطع و پایان اتاق حین reconnect. قطع موقت نباید UI را خروج نهایی اعلام کند؛ بازگشت نباید دستگاه خاموش را روشن کند.

## ۱۰. چت، تخته و فایل مشترک

چت tenant/session scoped، متن بدون HTML، pagination، سقف payload/rate، ارسال idempotent و moderation داشته باشد. delivered/pending/failed فقط از واقعیت شبکه گرفته شود. حذف/سکوت با نقش سرور، retention و audit انجام شود. history خصوصی برای عضو خارج‌شده قابل دسترس نباشد.

Yjs و WebSocket provider مستقل با auth زمان‌دار و ACL سند راه‌اندازی کن. board document به اتاق/سازمان وصل باشد؛ مجوز نوشتن جدا از دیدن، persistence، snapshot، سقف سند، resync و revocation کانال لازم‌اند. پاک‌کردن تختهٔ مشترک توسط میزبان تأیید داشته باشد. undo ترجیحاً تغییر خود کاربر را برگرداند. cursorهای متعدد باعث render سنگین کل صفحه نشوند.

فایل درس سقف type/size، اسکن بدافزار، storage خصوصی، اجازهٔ دانلود و انقضای لینک داشته باشد. SVG/HTML آپلودی بدون sanitize نمایش داده نشوند. کنترل مصرف فضای سازمان، حذف، retention و شکست نیمه‌کارهٔ upload طراحی شوند.

## ۱۱. ضبط واقعی توسط میزبان

RECORDING.md را اجرا کن: درخواست معتبر → رزرو ظرفیت → starting → recording → stopping → processing → ready/failed. موفقیت فقط پس از webhook امضاشده و metadata فایل تأییدشده. دکمهٔ کلیک‌شده یا job enqueue به معنی آغاز ضبط نیست.

Egress و worker با retry محدود، idempotency و queue واقعی، storage خصوصی S3 سازگار و lifecycle مستقل از مرورگر میزبان راه‌اندازی کن. template فارسی، تخته/اشتراک صفحه/گوینده و چینش خوانا داشته باشد. اعلان ضبط برای همه و سیاست رضایت قابل فهم باشد. قطع مرورگر میزبان نباید ضبط را بی‌صدا گم کند.

بازپخش با ACL سازمان/کلاس، URL امضاشدهٔ کوتاه‌عمر، مدت، حجم، تاریخ و وضعیت آماده/پردازش/خطا ارائه شود. سقف ضبط همزمان و فضای باقی‌مانده server enforced؛ حذف و retention واقعاً فایل و metadata را هماهنگ پاک کنند. آزمون آغاز تکراری، webhook تکراری/جعلی/خارج از ترتیب، قطع worker، خطای storage و پایان جلسه لازم است. حالت خصوصی E2EE در طراحی اولیه ضبط سمت سرور ندارد؛ این تفاوت را مخفی نکن.

## ۱۲. گزارش و عملیات

حضور و غیاب از intervalهای session و رویداد معتبر بساز؛ reconnect را غیبت/عضو تکراری حساب نکن. export گزارش با ACL، حد اندازه و دادهٔ کمینه باشد. تنظیم timezone و تاریخ فارسی فقط نمایش است؛ ذخیرهٔ زمان UTC و semantics روشن باشد.

لاگ ساختاریافته با correlationId، خطاهای بدون secret و telemetry بدون محتوای چت/درس/صدا ایجاد کن. readiness واقعی سرویس‌ها از liveness جدا باشد. heartbeat و alert با آستانهٔ تعریف‌شده و جلوگیری از اعلان تکراری. backup encrypted، restore آزمایشی، RPO/RTO مستند، incident runbook و rollback لازم‌اند.

سنجش performance بر اساس محیط، تعداد publisher/subscriber، bitrate، TURN و ضبط مشخص انجام شود. سناریوی اولیهٔ معماری یک هدف تست است، تضمین ظرفیت نیست. p95 ورود و API، reconnect، افت فریم/کیفیت، CPU/SFU، خروجی شبکه، رشد حافظه، باتری موبایل و هزینه را اندازه بگیر. فایل SDK رسانه در پنل مدیریت لود نشود. queryها pagination و index مناسب داشته باشند. از package، microservice یا Kubernetes تازه فقط با نیاز اثبات‌شده استفاده کن.

## ۱۳. امنیت و انتشار

احراز هویت و مجوز واقعی، CSRF/origin، rate limit، validation، audit، CSP با nonce و allowlist واقعی SFU/WebSocket، HSTS پس از HTTPS قطعی، private storage و دسترسی کوتاه‌عمر اجرا شوند. dependency audit و بررسی مستقل امنیت، از جمله IDOR/XSS/file upload/webhook/reconnect لازم است. عبارت «ضد هک» را تضمین مطلق نکن؛ کنترل، تست و محدودیت را گزارش کن.

در انتشار، team/project/environment/commit را تأیید کن. migration backward-compatible و برنامهٔ rollback قبل از release باشد. preview را تست کن و سپس production را منتشر کن. `.env.local`، tokenهای CLI/OIDC، فایل ضبط، اطلاعات واقعی دانش‌آموز و artifact تست هرگز commit یا upload نشوند. Git integration را فقط پس از تأیید اتصال واقعی فعال اعلام کن.

## ۱۴. تعریف پایان و تحویل هر مرحله

پیش از تحویل `npm run check` و `npm run build` پاس شوند. تست رفتاری منطق حساس، E2E مسیر کاربر و شبکه/رسانهٔ واقعی متناسب با تغییر اجرا شوند. برای تغییر ظاهری ساده تست آینه‌ای بی‌فایده نساز، ولی حفاظت tenant، سهمیه، ضبط و اتصال مجدد بدون آزمون تحویل داده نشوند.

نسخهٔ قابل استفاده باید این سناریوها را واقعاً پاس کند:

۱. مدیر سازمان مدرسه را می‌سازد، معلم و دانش‌آموز را دعوت می‌کند، کلاس و جلسهٔ معتبر تعریف می‌کند.
۲. دو سازمان با نقش‌های متفاوت هیچ داده، فایل، تیکت، کانال یا ضبط یکدیگر را نمی‌بینند.
۳. کاربران روی شبکه‌های متفاوت وارد کلاس واقعی می‌شوند؛ صدا/تصویر/صفحه و اجازهٔ صحبت مطابق grant کار می‌کنند.
۴. قطع شبکه و بازگشت بدون دورزدن ban و پایان اتاق انجام می‌شود؛ خروج همهٔ trackها را متوقف می‌کند.
۵. چت و تخته همزمان و پایدارند؛ فایل خصوصی با مجوز دانلود می‌شود.
۶. میزبان ضبط واقعی را شروع/متوقف می‌کند؛ فایل تأییدشده برای افراد مجاز بازپخش و طبق retention حذف می‌شود.
۷. سوپروایزر فقط سازمان خودش را می‌بیند؛ مشخصات میزبان/سرویس و ظرفیت از دادهٔ معتبر و با زمان سنجش نمایش داده می‌شوند.
۸. ثبت تیکت، پاسخ پشتیبانی و وضعیت/شمارهٔ پیگیری پس از commit واقعی کار می‌کنند؛ retry تیکت تکراری نمی‌سازد.
۹. تمام مسیرها dark/light، موبایل، کیبورد، permission denied، offline، error و reduced motion دارند.
۱۰. backup restore، rollback، load/network test و runbook همراه شواهد اجرا موجودند.

تحویل نهایی باید شامل لینک نسخه، commit، تغییر قابل مشاهده، آزمون‌های انجام‌شده، منابع داده، نیازهای تنظیم‌نشده و ریسک‌های باقیمانده باشد. ROADMAP را فقط برای موارد واقعاً تأییدشده علامت بزن. لندینگ و امکانات AI پس از پایداری هسته هستند؛ قابلیت ارائه‌نشده را برای بازاریابی وعده نده.

اکنون با بررسی مخزن شروع کن و نخستین مرحلهٔ وابستهٔ ناتمام را تا معیار پذیرش خودش کامل کن. درخواست مبهم «همه‌چیز تمام» را به فازهای قابل سنجش تبدیل کن؛ از ادامهٔ کار ضروری و مجاز خودداری نکن و هرگز تکمیل نمایشی را جای تکمیل واقعی گزارش نکن.
