# ADR 0001 — پایهٔ پلتفرم

تاریخ: 2026-10-13؛ وضعیت: پذیرفته‌شده برای پایهٔ پروژه، نیازمند آزمون ظرفیت.

## مسئله

کلاس‌های سازمانی نیاز به مدیریت اعضا و دادهٔ بادوام دارند، اما media real-time نباید CPU و شبکهٔ backend پنل را مصرف کند. اینترنت ضعیف، ضبط، دسترسی supervisor و تفاوت نقش مدرس/دانش‌آموز جزء الزامات هستند.

## تصمیم

Next.js modular monolith برای control plane، PostgreSQL برای داده، LiveKit SFU برای WebRTC، Redis برای coordination و rate limiting، Yjs برای تخته و Egress/S3 برای ضبط. UI فارسی RTL با CSS tokens و dark/light. auth با Better Auth در فاز حساب؛ server policy مستقل از کتابخانهٔ auth.

## گزینه‌های بررسی‌شده

Mesh WebRTC به ازای هر شرکت‌کننده مصرف upload را بالا می‌برد؛ برای کلاس انتخاب نشد. توسعهٔ SFU از صفر زمان و ریسک زیادی دارد. سرویس‌های ویدیویی تجاری ممکن‌اند، ولی نیاز میزبانی و کنترل را محدود می‌کنند. BigBlueButton گزینهٔ مناسب آموزش آماده است، ولی برای محصول با UI و دامنهٔ سفارشی، LiveKit انتخاب اولیه است. Laravel برای پنل ممکن است اما زنجیرهٔ TypeScript واحد، اشتراک type و یک tooling را ترجیح می‌دهیم؛ LiveKit همچنان مستقل است.

## پیامدها

میزبانی رسانه به UDP، TLS/TURN و پهنای باند واقعی نیاز دارد؛ Laragon فقط محیط سورس و توسعه است. recording worker و realtime process جدا deployment می‌شوند. E2EE با ضبط معمول سمت سرور جمع نمی‌شود مگر recorder دارای کلید شود. هیچ وعدهٔ ظرفیت قبل از load test. قابلیت‌های انتخاب‌شده الزاماً در فاز صفر پیاده نشده‌اند؛ roadmap مرجع وضعیت است.
